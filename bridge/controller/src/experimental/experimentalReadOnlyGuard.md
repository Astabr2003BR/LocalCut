# Experimental read-only guard — disconnected prototype

This is a standalone, opt-in authorization prototype, NOT a relay endpoint or an integration. It does not change the current production router, device pairing, transport, device application, or policy. Do not deploy or rely on it as an access boundary without integration and review.

The existing router checks the stored controller/device association and protocol types, but its capability set includes writes and its completed-result cache is not a replay authorization mechanism. Existing pairing verifies a device challenge with its stored public key; that alone does not bind a controller request, project and read-only scope. This experiment introduces an independent proposed signed-grant and signed-command contract; the present relay and Android client do not implement it.

- An independently trusted Ed25519 authority signs a grant for one controller public key, authenticated controller, device, project, explicit permitted read scopes and one randomly generated guard-instance epoch. Grant duration is at most 5 minutes. The controller proves possession of the granted private key by signing each entire command and grant signature. Canonical signature bytes are the fixed arrays produced by the exported functions, with domain separation.
- Only `get_device_status` is accepted, with an exactly empty object payload, exact fields and a null revision. Every other command is denied. Even status may disclose project data: response filtering, authorization and confidentiality are necessary.
- Validity is inclusive at issue time, exclusive at expiry. Commands must fit within the grant, last at most 30 seconds, and not be future-issued. The guard compares wall and monotonic clock progress and permanently fails closed for that epoch if their difference exceeds two seconds; a trustworthy clock is still required.
- Both a 32-byte nonce and message ID are reserved atomically inside the synchronous guard. Repeats are rejected; entries are retained until grant expiry. Capacity exhaustion fails closed. There is no eviction of live entries. Each guard has an unpredictable epoch; old grants fail on restart and grants for one instance fail at another. These in-memory guarantees are per instance: do not clone a guard's state/epoch or split one authorization boundary across instances. A distributed or persistent deployment needs separately designed atomic replay protection. Recheck expiry at the final dispatch boundary; do not queue an authorized command past its expiry.
- `verifyLiveBinding` is mandatory and must synchronously return literal `true` only after verifying the *current*, non-revoked controller/device/project/key pairing and the authenticated controller and device channels. It must be bound to trusted authenticated connection state, not user-provided identifiers. A promise, exception or other value denies. The caller must supply `authenticatedControllerId` from that trusted state. No implementation of this trust bridge is supplied here. Pairing approval must not be delegated to an external activity. Revocation must also close/invalidate the active device channel; a race between this check and send requires an integration-level atomic strategy.
- Obtain the authority verification key out of band from trusted configuration. Never accept it from requests. Grant issuance must independently verify the current pairing, requested scopes and consent; no authority issuer is implemented here. Do not expose signing keys, grants, nonces, request IDs or channel credentials in logs/responses. Secure the transport and bind its authenticated endpoints. Do not forward raw JSON: forward only the returned reconstructed object, and deny on null. Reject any alternate path that could bypass the guard. Review caching and avoid serving results across identities or reusing message IDs. Ensure result data is scoped and redacted as appropriate.
- Signing keys here use Ed25519; the existing device pairing uses a different verification contract. There is no claim of compatibility. Local trusted authority, live binding, secure identity, user consent, device-side enforcement, key lifecycle/revocation, response privacy, integration, security review and real-device validation remain open.

Test separately with `node --test test/experimentalReadOnlyGuard.test.mjs` from `bridge/controller`. This JavaScript test is deliberately not matched by the existing `test/*.test.ts` npm script; no existing script was edited. Node 20 can execute these isolated tests, but the controller package specifies Node 24.12.x for its normal suite.
