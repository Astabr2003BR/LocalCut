# Experimental blocked relay simulation

This is an isolated, intentionally non-operational experiment. It is NOT a relay, transport, route, production change, authorization boundary, or device integration. No server imports it. Opt-in must be the literal Boolean `true`; it is off by default. Even with opt-in and a valid authority key, live binding is hardcoded false, there is no dispatch function, and every evaluation returns only the sanitized blocked status. With no opt-in it returns only the disabled status. The wrapper has no log, persistence, or channel. It deliberately never exposes the guard epoch, so external grant issuance and successful use are not implemented. Do not add this to a server or enable it in production.

## Future design, not implemented or authorized for deployment

- Establish an end-to-end authenticated controller/device channel, a separately trusted authority and an explicit, revocable on-device consent that binds controller key, device, project and read-only scope. Existing pairing and sessions alone do not demonstrate this full binding. No codes, request IDs, temporary URLs, tokens or credentials in logs or responses; report only sanitized status.
- Design and audit an atomic revocation/expiry/check-and-send boundary with appropriate channel closure, replay handling across any instances, rate and resource limits, and a filtered status-only response. Enforce the allowlist on the device too. Ensure no direct or alternate production relay path can bypass the policy; do not use an ambiguous relay. Never dispatch raw input; never dispatch writes.
- The current `CommandRouter.execute` accepts a broad production capability set and has per-device/message caches, while `WebSocketDeviceChannel.send` forwards command JSON. Direct reuse without a separate security design may bypass the guard, reuse cached data across identities or race revocation/expiry. A guarded, isolated transport would need an authenticated identity sourced from the connection, current consent and scoped binding, explicit lifecycle and an atomic final send. No such transport is supplied here.
- A real integration requires a compatible client/issuer protocol, trusted key management, authenticated epoch distribution, reviewed device-side enforcement and response redaction, security review, and real-device tests. Do not replace the hardcoded false with an injectable flag or claim that a signed grant alone establishes consent.

Run the isolated tests from `bridge/controller` with `node --test test/experimentalReadOnlyGuard.test.mjs test/experimentalBlockedRelay.test.mjs`. These `.mjs` tests are not included in the existing npm test script. The controller package requires Node 24.12.x for its normal suite; success on another Node version is not full package validation.
